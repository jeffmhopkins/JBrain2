# Self-hosted browser agent options — prior-art survey

> **Status:** Research · **Last verified:** 2026-10-04 · Feeds `../../plans/BROWSER_AGENT_PLAN.md`.

## Summary

For JBrain2, the best option is to adopt rather than build. Run **Microsoft's official `playwright-mcp` container** as a new Compose sidecar using its HTTP transport. Drive it from a **dedicated browsing sub-agent inside the FastAPI backend**. That sub-agent has its own context window, its own step budget and its own llama.cpp tool-calling loop through the existing LLM adapter. It hands back only a short, quarantined text result to the main assistant. This pairing matches what a ~6B-active local model can actually do. playwright-mcp observes pages through a pruned accessibility tree with element refs, so each step is one small tool call and the model never emits pixel coordinates or fills a large nested JSON schema. The popular agent frameworks (browser-use, Stagehand) need exactly those large schemas, and their own docs and maintainers say small Qwen models fail at it. The real safety boundary is the network, not the tool flags. The browser must sit on its own Docker network that reaches the internet only through an egress proxy that denies private address ranges. It must never share a network with Postgres. Today the box's `reader` and `byparr` services both sit on the shared `internal` network alongside the database, so a new browser must not follow that pattern. For search, pinning SearXNG to `2026.10.2-19ffbcd30` is very likely the main fix: it includes the 2026-09-04 curl_cffi migration, which unblocked Brave, Startpage and Qwant for another home operator. Turn on Bing, put a rate-limited queue in front of SearXNG, and use Brave's or Mojeek's metered API as a cheap fallback. With those in place, Tavily can be dropped to an optional last tier. Nobody has published browser-agent results for a "Qwen3.8 Flash-Next" model, so the on-box bake-off described at the end decides whether this ships, not the benchmarks.

## Snapshot-driven MCP servers beat agent frameworks for a 6B-active model

The candidate field falls into two families. The first is **agent frameworks that own the observe→act loop**: browser-use, Stagehand, Skyvern and Notte. The second is **tool servers with no LLM of their own**, where the host runs the loop: playwright-mcp, Vercel's agent-browser and Google's chrome-devtools-mcp. For a box whose non-negotiable #1 says every LLM call goes through JBrain2's own adapter, the second family is the natural fit. The model loop stays in JBrain2's code, uses its adapter, and logs to its run-log. An embedded framework would instead make its own calls to an OpenAI-compatible endpoint.

The evidence against framework-owned loops on small models is specific. browser-use's model docs warn that for Qwen "only `qwen-vl-max` works reliably; smaller variants have schema formatting issues" ([browser-use supported models](https://docs.browser-use.com/supported-models)). A September 2026 field test is telling. Small Qwen models emitted `{"navigate": "google.com"}` instead of the nested `{"navigate": {"url": …}}`. browser-use 0.13.8 with local `qwen3:4b` failed at step one after **four 75-second model timeouts**, while the same browser layer without the LLM finished the task in **4.92 s** ([ego lite](https://lite.ego.app/article/browser-use-local-llm)). In April 2026, a Stagehand user connected `qwen2.5-coder:7b` and found it "consistently failed" Zod schema validation. A maintainer replied that failures with strict JSON validation are model limits, not integration bugs ([Stagehand discussion #1303](https://github.com/browserbase/stagehand/discussions/1303)). By contrast, playwright-mcp's snapshot mode needs "no vision models" and "operates purely on structured data" ([playwright-mcp README](https://github.com/microsoft/playwright-mcp)). The model only has to pick a tool such as `browser_click` and pass a ref, which is the job llama.cpp tool calling already does for the assistant.

The research on small models supports the same design. On WebArena, **base Qwen3.5-9B scored 31.0%** using an accessibility tree plus a screenshot, against 51.2% for Gemini 3 Pro. Its characteristic failure was aimless wandering through filters ([arXiv 2604.07776](https://arxiv.org/html/2604.07776)). MolmoWeb's ablation found that **an AxTree plus a screenshot (69–72%) beat set-of-marks (56%)** ([arXiv 2604.08516](https://arxiv.org/html/2604.08516)). Fine-tuned 4–9B specialists have closed much of the gap. Fara1.5-9B reaches 63.4% on Online-Mind2Web ([Microsoft Research](https://www.microsoft.com/en-us/research/articles/fara1-5-computer-use-agent/)). But these specialists act through screenshots and pixel coordinates in their own harness, not through OpenAI tool calls, and no GGUF or llama.cpp report for Fara1.5 was found. For a general-purpose instruct model, the right shape is therefore text-first refs, a screenshot only when needed, a small flat action set, and short tasks. Picking a theater location and reading back showtimes is close to the 8–14 steps that typical benchmark tasks need.

Two candidates stand out, and they are closer than the star counts suggest. **playwright-mcp wins on packaging.** It has a first-party Microsoft image and an HTTP transport, so it drops into Compose as a service the backend calls over the network. It also has the most mature Playwright engine underneath ([playwright-mcp README](https://github.com/microsoft/playwright-mcp)). **agent-browser wins on built-in guardrails and token thrift.** It offers action policies that gate destructive operations, confirmation prompts, "content boundary markers", and delta snapshots ([vercel-labs/agent-browser](https://github.com/vercel-labs/agent-browser)). Both of those would otherwise have to be built in the host loop. Its packaging is weaker for this box: it is a Rust CLI with "Docker support" but no confirmed official image. One more point matters: Playwright's own README now says its CLI is more token-efficient than MCP for coding agents, while MCP remains the choice for "persistent state, rich introspection, and iterative reasoning" ([playwright-mcp README](https://github.com/microsoft/playwright-mcp)). Multi-step browsing is the iterative case, so MCP is the right fit here. Snapshot size is still the variable to measure, because an AxTree can run to **tens of thousands of tokens per page** ([arXiv 2604.08516](https://arxiv.org/html/2604.08516)).

**Skyvern** is the strongest "whole product" option. It is the only one with a documented, first-class OpenAI-compatible-endpoint path and a vision-first loop ([Skyvern Local LLMs](https://www.skyvern.com/docs/integrations/local-llms)). But it brings a second Postgres, a UI and AGPL code, and its loop would sit outside JBrain2's adapter, run-log and RLS. That makes it a fallback to revisit if form-filling "write" tasks become the main workload. It should not be the first adoption.

## Run the browser in its own sidecar, with stealth as an escalation

The runtime question is simpler than it looks, because playwright-mcp's image bundles its own Chromium. A separate browser-infrastructure service such as Steel or Browserless is only worth adding for a feature playwright-mcp lacks.

| Runtime | License | Image | Protocol | Stealth (2026 Cloudflare benchmark, 31 targets) | Notes |
|---|---|---|---|---|---|
| playwright-mcp's bundled Chromium | Apache-2.0 | `mcr.microsoft.com/playwright/mcp` | Internal | Vanilla Playwright: 24 OK / 2 gated / 5 blocked | Simplest; no live view |
| Steel | Apache-2.0 | `ghcr.io/steel-dev/steel-browser` | REST + CDP (9223) | Advertises stealth plugins; not benchmarked | Session viewer; every release still "-beta" |
| Browserless OSS | **SSPL-1.0 or commercial** | `ghcr.io/browserless/chromium` | CDP WebSocket | Stealth is Enterprise-only | Most active (v2.57.0, 2026-09-30); unauthenticated `/function` if no TOKEN |
| kernel-images | Apache-2.0 | kernel/kernel-images | CDP (9222) | None documented | Best live view (WebRTC/noVNC) and MP4 recording |
| Patchright | Apache-2.0 | Library only | Playwright drop-in | 25 / 3 / 3 | Chromium-only; console disabled |
| nodriver / zendriver | AGPL-3.0 | zendriver-docker | Raw CDP | **28 / 3 / 0**, only tool with zero hard blocks | Headed under Xvfb recommended |
| CloakBrowser | MIT wrapper, **proprietary binary** | `cloakhq/cloakbrowser` | CDP (`cloakserve`) | 26 / 3 / 2 | v148+ needs a paid Pro subscription |
| Camoufox (inside Byparr) | MPL-2.0 / GPL-3.0 | `ghcr.io/thephaseless/byparr` | Playwright-Firefox (Juggler) + FlareSolverr HTTP API, **not CDP** | 25 / 3 / 3 (old Firefox 135 build tested) | Already on the box |
| Lightpanda | AGPL-3.0 | `lightpanda/browser:nightly` | CDP | None | 123 MB for 100 pages vs Chromium's 2 GB; incomplete Web APIs |

The stealth figures come from an independent 2026 benchmark. It ran 7 tools against 31 Cloudflare targets over 3 sweeps, from a residential IP, in headed mode ([Paterson benchmark](https://ianlpaterson.com/blog/anti-detect-browser-benchmark-patchright-nodriver-curl-cffi/)). The other columns come from each project's repo or docs ([Steel](https://github.com/steel-dev/steel-browser), [Browserless](https://github.com/browserless/browserless), [kernel-images](https://github.com/kernel/kernel-images), [CloakBrowser](https://github.com/CloakHQ/cloakbrowser), [Byparr](https://github.com/ThePhaseless/Byparr), [Lightpanda](https://github.com/lightpanda-io/browser)).

Read with care, the benchmark says **stealth spreads are narrow and the residential IP matters more than the tool**. Vanilla Playwright cleared 24 of 31 Cloudflare targets, against 28 for the best tool, nodriver. The author attributes the gap to protocol traces that Playwright leaves and raw CDP avoids ([Paterson benchmark](https://ianlpaterson.com/blog/anti-detect-browser-benchmark-patchright-nodriver-curl-cffi/)). A theater chain's showtime page is far more likely to need JavaScript than to need anti-bot evasion. So the sensible default is stock playwright-mcp. When a site walls the browser, the web_fetch ladder's Byparr leg already exists for read-only fetches.

Camoufox, and therefore Byparr, speaks the Playwright-Firefox protocol rather than CDP. Byparr also exposes a FlareSolverr-style HTTP API that returns cookies and HTML, not a session an agent can drive. So the browsing agent **cannot simply attach to Byparr** ([Byparr](https://github.com/ThePhaseless/Byparr); [Camoufox](https://github.com/daijro/camoufox)). If stealth turns out to matter for interactive tasks, the upgrade path is to launch real Chrome through zendriver (or CloakBrowser's free v146 binary) in its own container. playwright-mcp would then attach to it over CDP. That attach option was not verified in this research, and an attaching Playwright client may reintroduce the very traces nodriver avoids. Licensing rules out the obvious "infrastructure" upgrades for a box like this. Browserless's SSPL requires a commercial license for closed-source or CI use, and CloakBrowser's newer binaries are paywalled. Steel and kernel-images are both Apache-2.0 and are the right choices if a **live view in the PWA** becomes a requirement. kernel-images streams the browser over WebRTC or noVNC and records MP4 through an API ([kernel-images](https://github.com/kernel/kernel-images)). Until then, a per-step screenshot written through the storage abstraction gives the owner a step-by-step view at near-zero cost.

## A quarantined sub-agent, fenced by the network rather than the prompt

The owner wants browsing to run in a sub-agent with its own context, never in the main assistant's context. That is also the strongest security choice available. **Indirect prompt injection from web content still succeeded 42–68% of the time** against NanoBrowser and BrowserUse in StakeBench's 3,168 adversarial runs. Swapping in a weaker model raised attack success by up to **26.5 points**, and "no single attack scenario was consistently blocked" ([CSO Online](https://www.csoonline.com/article/4184455/prompt-injection-breaks-todays-ai-agents-study-warns.html)). A ~6B-active local model should be assumed to be at the injectable end of that range. The design therefore has to make a successful injection harmless rather than try to make it unlikely.

The governing principle is Meta's **Agents Rule of Two**. An agent may have at most two of three properties: it processes untrusted input, it can access sensitive data, and it can change state or communicate externally ([Simon Willison](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). The browsing sub-agent gets only the first. Its system prompt contains the task and nothing from the owner's notes, wiki, health, finance or location domains. It holds no credentials, and it uses an `--isolated` in-memory profile. Its output goes back to the parent as **quarantined data**, following the Dual-LLM and context-minimization patterns: a capped-length text answer plus the source URLs ([arXiv 2506.08837](https://arxiv.org/abs/2506.08837)). The parent may quote or cite that result. It must never let the result choose a side-effecting tool or its arguments. Markdown images and links should be stripped so a poisoned page cannot turn the answer into an exfiltration beacon. If the parent itself has rich context, the sub-agent's task string must be written so that it carries only what the site needs to know. "Showtimes for Dune at the Regal nearest ZIP 98101" is fine. Anything drawn from the location domain should go out only with the owner's explicit consent, because that query is itself egress.

**The fence has to be built below the browser.** Playwright's own docs call its origin lists "convenience defenses… not a security boundary — they do not affect redirects and can be worked around deliberately" ([Playwright MCP options](https://playwright.dev/mcp/configuration/options)). The failure mode is real. A playwright-mcp setup with no blocked origins let a prompt-injected agent screenshot the cloud metadata endpoint 169.254.169.254 into a public PR ([VibeCoder #1292](https://github.com/stSoftwareAU/VibeCoder/issues/1292)). browser-use has open 2026 issues on `data:`/`blob:` URLs bypassing `allowed_domains` and on IP URLs being unblocked by default ([#4763](https://github.com/browser-use/browser-use/issues/4763), [#5879](https://github.com/browser-use/browser-use/issues/5879)).

The compose file already has the right pattern: the egress-free `render` and `sandbox` networks, which only the api and one sidecar join. The browser needs a variant of that pattern. It goes on its own `browser` network that only the api (to call MCP over HTTP) and a small egress proxy join. The proxy resolves DNS itself, which defeats rebinding. It denies RFC1918, loopback, link-local (including 169.254/16), CGNAT 100.64/10, and IPv6 ULA and link-local ranges, plus every Compose service name. The browser container has no route to `internal`, where `db`, `supervisor` and the model servers live. playwright-mcp's `--proxy-server` flag points it at that proxy. Docker's network membership is what makes the claim true. Following the existing `test_pysandbox_server.py` precedent, a compose test should assert that membership.

The remaining guardrails live in the host loop, where JBrain2 controls them. The action set should be **read-only by default**: navigate, click, type into search and filter fields, select, scroll, snapshot, extract. Form submissions on checkout or login pages, downloads, uploads and payments are refused, or routed to an owner confirmation card in the PWA. agent-browser's action policies are a ready model for that card ([vercel-labs/agent-browser](https://github.com/vercel-labs/agent-browser)). Budgets should be explicit: about **15–25 steps**, playwright-mcp's 60 s navigation timeout, a few minutes of wall-clock time per task, and a context of at least 64k tokens with history truncated to the last few snapshots ([ego lite](https://lite.ego.app/article/browser-use-local-llm); [Playwright MCP options](https://playwright.dev/mcp/configuration/options)). Loop detection should stop the "wanders through filters for 10 steps" failure that WebArena documented for small models ([arXiv 2604.07776](https://arxiv.org/html/2604.07776)). Success must be verified independently, for example by checking that the extracted answer is actually present in the final snapshot, instead of trusting the agent's own "done" flag. Two plumbing details cause most local-model failures. First, the streaming tool-call handler must keep thinking, content and tool_calls chunks together ([ego lite](https://lite.ego.app/article/browser-use-local-llm)). Second, llama-server must parse the model's chat template, normally with `--jinja`. Both live in JBrain2's adapter and are worth a dedicated test.

Two operational points follow from rule 10: the owner has no terminal. The playwright-mcp image should be **pinned by tag and bumped by the update script**, not left on `latest`. The same audit applies to `reader` (`ghcr.io/intergalacticalvariable/reader:latest`) and `byparr` (`ghcr.io/thephaseless/byparr:latest`), which currently carry the same stale-`latest` hazard that left SearXNG months behind. The browser sub-agent's enable flag, its per-domain confirmation policy, and its run-log of step screenshots all belong in the PWA's Settings and Ops surfaces from day one.

## SearXNG's pin is the search fix; metered APIs are the backstop

The blocking pattern on the box matches a published case exactly. A home-ops operator on image 2026.5.29 saw DuckDuckGo CAPTCHA, Startpage suspended for CAPTCHA, Brave suspended for "too many requests", and Qwant "access denied". **Upgrading to 2026.9.17 "fixed the engines outright"**, returning 27–29 results per query, with only DuckDuckGo still CAPTCHA'd. Bing worked throughout, though it is disabled by default ([home-ops#1034](https://github.com/MarkNygaard/home-ops/pull/1034)). The cause was SearXNG's old httpx client, whose TLS and header fingerprints engines recognise as a bot. **PR #6620, merged 2026-09-04, moved SearXNG to curl_cffi** with Chrome impersonation by default. It explicitly closed the Google-blocking and DuckDuckGo-CAPTCHA issues and needs no user configuration ([searxng PR #6620](https://github.com/searxng/searxng/pull/6620)). The new pin `2026.10.2-19ffbcd30` postdates that merge. So the cheapest, most likely fix is already in place, provided the update script now actually pulls it.

Three settings should follow. First, enable `bing` and the low-block structured engines that suit an agent: Wikipedia, Wikidata, GitHub, StackExchange and arXiv. Down-weight DuckDuckGo. Its bot blocker bans the IP, and the documented unblock is a query from a real browser on that IP ([SearXNG DDG docs](https://docs.searxng.org/dev/engines/online/duckduckgo.html)). Second, retune `suspended_times`. The defaults suspend an engine for **86,400 s on a CAPTCHA or 403, 3,600 s on a 429, 7 days on a Google reCAPTCHA, and 15 days on a Cloudflare CAPTCHA** ([search settings](https://docs.searxng.org/admin/settings/settings_search.html)). One deep-research burst can therefore silently remove an engine for a day. Shorter suspensions, plus engine-suspension state shown in the Ops UI, make that visible and recoverable without a terminal. Third, put a backend-side queue in front of SearXNG that caps concurrency, spaces requests with jitter and caches repeat queries. Dozens of queries in a few minutes is the load that trips upstream limits. Mojeek's 403 is the one symptom the upgrade evidence does not cover. SearXNG's `limiter` plugin will not help, because it guards the instance against inbound bots, not outbound blocks.

Behind SearXNG, a provider chain with per-provider budgets removes the dependency on Tavily. Brave's Search API gives a **$5 automatic monthly credit (about 1,000 queries), then $5 per 1,000, at 50 QPS**. That rate absorbs bursts ([Brave Search API](https://brave.com/search/api/)). Mojeek's independent index costs **£2 per 1,000** and explicitly allows AI use ([Mojeek API](https://www.mojeek.com/services/search/web-search-api/)). Serper ($0.30–1.00 per 1,000) is the cheapest route to Google-quality results ([Parallel](https://parallel.ai/articles/best-free-web-search-api)). Two dead ends should be avoided: the Bing Search API was retired on 2025-08-11 ([Microsoft](https://learn.microsoft.com/en-us/lifecycle/announcements/bing-search-api-retirement)), and Google Custom Search shuts down on 2027-01-01 ([heise](https://www.heise.de/en/news/Google-is-discontinuing-its-free-web-search-index-for-developers-11152411.html)). Self-hosted replacements do not replace a major index. Whoogle was archived on 2026-08-14 after Google killed its last working user agent ([whoogle-search](https://github.com/benbusby/whoogle-search)). 4get and LibreY scrape the same upstreams, and YaCy is useful only as a niche index of the owner's own frequently cited domains.

Driving a search engine through the new browser sub-agent is the last resort, not the plan. It works at low volume, but a challenge costs tens of seconds. Google has required JavaScript since January 2025 and treats automated querying as a violation of its policies ([Oxylabs](https://oxylabs.io/blog/google-search-javascript)). The browser fallback should run serialized, use a persistent context, and fire only when SearXNG and the metered APIs come back thin.

## Risks and what to measure before committing

The largest risk is **the model, not the plumbing**. No browser-agent benchmark exists for Qwen3.8 Flash-Next or any ~6B-active MoE. The closest data point, zero-shot Qwen3.5-9B at 31% on WebArena, warns that general small models lose their way on long tasks ([arXiv 2604.07776](https://arxiv.org/html/2604.07776)). The next risk is snapshot size. An AxTree that runs to tens of thousands of tokens on a busy cinema site will crowd the context and slow every step. Third is injection: a capable sub-agent on a weak model will be talked into things, and only the network fence and the read-only action gate contain that. Fourth is upstream drift. playwright-mcp removed its origin flags in v0.0.47 and later restored them ([playwright-mcp #1210](https://github.com/microsoft/playwright-mcp/issues/1210)), so pinned image tags and a regression suite matter more than any single flag. Finally, the search fix is supported by one operator's evidence. Whether it holds on this IP, especially for Mojeek, is still unknown.

Five on-box measurements should decide adoption.

1. **Task success.** Run a fixed set of 20–30 of the owner's real tasks: theater location pickers, opening hours behind JS, a store-stock check, a multi-page table read. Run them through playwright-mcp and through agent-browser with the same host loop. Record success, verified against the final page and not the model's own claim, steps per task, and wall-clock time.
2. **Per-step cost.** Measure snapshot tokens, model latency, and the tool-call parse-failure rate under llama-server. Repeat with interactive-only or delta snapshots and with screenshots on demand.
3. **Fence tests.** These must fail closed. Navigate to 169.254.169.254, an RFC1918 address, `db:5432` and `searxng:8080`, through a redirect and through a DNS-rebinding hostname. Run a canary page carrying an injected instruction to call a tool or leak a string.
4. **SearXNG under the new pin, for a week.** Track per-engine success, suspension events, and results per query during a synthetic 50-query burst. This decides whether Brave's free credit covers the overflow or a paid tier is needed.
5. **Resources.** Measure the RSS and idle cost of the browser container next to the resident local models on the box's unified memory.

## Conclusion

Every competent open framework now assumes a frontier model, so the decisive design choice for a 6B-active local model is **how little the model must do per step**. A snapshot-and-ref tool server gives the box the smallest per-step decision available without fine-tuning a specialist, which is why the ten-times-more-starred browser-use loses here. The same logic holds for safety. The model is the weakest link in an injection attack, so containment has to live in Docker networks, the proxy and the host loop's action gate, all of which JBrain2 already knows how to build and test. The sub-agent boundary the owner asked for is the mechanism that makes the Rule of Two enforceable, not just a way to keep context clean.

The SearXNG episode carries a lesson broader than search. A `latest` tag that the updater never re-pulls quietly turned a solved upstream problem into months of "the IP is burned". Both new and existing sidecars (`reader`, `byparr`, the coming playwright-mcp) should be pinned and moved forward by the update path the owner can trigger from the PWA. If the on-box bake-off shows the local model cannot clear its own theater-picker task at a useful rate, the fallback is not a different framework. It is a Qwen-based browser specialist such as Fara1.5-9B, once someone proves it runs under llama.cpp. Watch for that.
